# Delivery Lease — Design

Status: **design**, not yet implemented.
Last updated: 2026-09-10 (rev 7 — atomicity scope, lost-event degradation;
rev 6 — failure-mode summary; rev 5 — abandonment outcome reconciliation,

Supersedes the informal in-flight tracking described in

## 1. Problem

### 1.0 Failure mode

The system's guarantee is that a telemetry record stays in PSRAM until the
bridge confirms it reached InfluxDB. That guarantee is enforced by state no
single component owns: *which record is currently being delivered* is spread
across a boolean flag, two identity globals, and the ring buffer's read
index — written at different moments, by different tasks, on different
cores, with nothing keeping them consistent.

Two consequences follow independently. At capacity, the overflow policy evicts
the record currently awaiting acknowledgment — and, between the ACK handler's
identity check and its removal step, can cause a *different*, unacknowledged
record to be discarded instead. Separately, because a record's identity is
published-then-recorded rather than assigned at selection, a stale
acknowledgment can clear the in-flight marker for a record that is still in
flight, causing it to be published twice. The first is silent data loss; the
second is duplication. Neither requires the other to occur.

"Silent" is literal: the eviction counter is never read anywhere in the
firmware — `droppedCount()` and `getStats()` have zero call sites — so the
device cannot distinguish a record it deliberately dropped from one it lost to
a bug.

**Why this survived validation.** Every overflow-dependent path requires a full
50,000-record ring, ~6.9 hours of undrained buffering at 2 Hz. The run that
certified the ACK-gated design used 570 records — 1.1% of capacity. These paths
were not missed by inspection; they were structurally unreachable in every test
ever run against this firmware.

Sections 1.1 and 1.2 are those two independently triggerable lease defects and
1.3 is their shared root cause. Section 1.4 is a separate latent transport
defect that can turn the head-of-line risk in 1.5 into a deterministic
failure.

### 1.1 Overflow can destroy an unresolved retry head

`BufferManager::push()` evicts the oldest record when `_count == _capacity`
(`BufferManager.cpp`, the `if (_count == _capacity)` block). The oldest record
is also the record currently selected for delivery. Two consequences:

- A record published but not yet ACKed can be evicted, defeating the retry
  guarantee. No stale ACK is required to trigger this.
- Worse: the ACK commit path does `peek()` at `main.cpp:514`, validates
  identity, then `pop()` at `main.cpp:517`. `filterTask` runs on core 1 and can
  `push()` between those two calls. On a full buffer that push evicts the
  validated record, and `pop()` then removes and silently discards **a
  different, un-ACKed record**.

Precondition for both: a full ring. At `PSRAM_BUFFER_CAPACITY = 50000` and 2 Hz
production, saturation takes ~6.9 hours of undrained buffering, or less under
the degraded-ACK regime where drain (~0.33 rec/s) falls below production.

### 1.2 Delivery identity is established after the fact

`mqttEnqueueTelemetry()` sets `g_bufferRecordInFlight` at `main.cpp:190`, but
`g_inFlightBoot` / `g_inFlightSeq` are written only after a successful publish
(`main.cpp:549-550`). They are never reset — not on commit, timeout
(`main.cpp:537`), disconnect (`main.cpp:478`), publish failure (`main.cpp:555`),
or enqueue failure (`main.cpp:202`).

So between enqueue and publish, the flag says "in flight" while the identity
names the *previous* record. An ACK arriving in that window takes the match
branch, peeks a head that no longer matches, and clears the flag at
`main.cpp:523` while a record is genuinely in flight — producing a duplicate
publish. Requires no full buffer.

The duplicate ACK that triggers it is generated by the firmware itself: on ACK
timeout the head is republished, and the bridge writes and ACKs unconditionally
per received record (`mqtt_to_influx.py:62`, called at 92 and 144, no dedupe),
so one record yields two ACKs.

Application-level retry is sufficient to produce the stale ACK.
Persistent-session redelivery across reconnect is not required, and is disabled
by the clean-session connection — `MqttManager.cpp:153` calls
`connect(_clientId)`, which PubSubClient delegates with `cleanSession = 1`
(`PubSubClient.cpp:170`, flag `0x02` at 219). That rules out cross-reconnect
redelivery specifically; it does not rule out all QoS 1 duplicate delivery
within an active session.

### 1.3 Root cause

Delivery state is split across unrelated globals and the ring buffer, with no
atomic owner of the record lease. Fixing either symptom alone leaves the other.

### 1.4 MQTT payload ceiling (latent, enables 1.5)

`MqttManager` never calls `setBufferSize()`, so PubSubClient uses its default
`MQTT_MAX_PACKET_SIZE = 256` (`PubSubClient.h:26`), while `config.h` declares
`MQTT_PAYLOAD_SIZE = 320`. Current telemetry packets are ~165-195 bytes
including topic and fixed header, so this is not a live failure — but the
declared budget exceeds the transport's capacity by 64 bytes, and `publish()`
returns false silently past that boundary. Any payload growth crosses it
deterministically. Fix by defining an `MQTT_CLIENT_BUFFER_SIZE` that covers the
maximum payload length, longest topic, two-byte topic-length field, and
PubSubClient's five-byte header reservation. Add a compile-time assertion tying
those constants together, call `setBufferSize(MQTT_CLIENT_BUFFER_SIZE)`, and
check its boolean result. The assertion proves the configured size is
sufficient; the runtime check proves the allocation actually succeeded.
`MqttManager::begin()` must surface allocation failure so setup can fail visibly
rather than silently continuing with the 256-byte default.

### 1.5 Head-of-line blocking

Pinning the head fixes 1.1 but introduces a bounded-progress requirement.
Delivery is strictly one record at a time from the head. A pinned record that
can never be ACKed stalls the drain to **zero** — every record behind it becomes
undeliverable while the buffer keeps rotating fresh data.

Note the pin's *capacity* cost is one slot, not an ongoing loss rate: at
saturation the ring sheds one record per arrival under any policy. Second-oldest
eviction changes which record is shed, not how many.

## 2. Invariant

> A record selected for delivery remains pinned until a matching ACK commits it
> or an explicit, counted abandonment releases it.

An explicit abandonment policy is mandatory for bounded progress: finite
capacity already forces some loss under sustained pressure, while an unACKable
pin would additionally block delivery of every retained record behind it.

## 3. Ownership

| Component | Owns | May not |
|---|---|---|
| `BufferManager` | Ring layout, pinned identity, pinned-record relocation, overflow and pressure counters — all under its mutex | Release a pin autonomously |
| `filterTask`, `sensorTask` | Call `push()` and forward any returned loss identity to `LossJournal`. May relocate the pinned record and increment pressure counters as a side effect of overflow | Acquire, commit, abandon, or release a pin |
| `connectionTask` | **Sole** caller of acquire / commit / abandon. Owns phase, `ever_published`, publish counters, and timers; owns generation only in the future deferred design | — |
| `telemetryTask`, `syncTask` | Signal that delivery is due (cadence only) | Create or mutate a lease; call `peek()` |
| `safetyTask`, other publishers | Enqueue non-leased messages (E-Stop) onto `g_publishQueue` | Affect telemetry delivery state |
| `LossJournal` | Thread-safe compression and bounded RAM retention of exact loss identities/ranges | Mutate the telemetry ring or lease |

Single-writer discipline for lease state is what makes commit and abandonment
race-free by construction rather than by argument. `push()` recording pressure
while `connectionTask` acts on it is deliberate: a `push()` that could release a
pin reintroduces a cross-core check-then-act race with the publish path.

### 3.1 Required task-architecture change

Today `telemetryTask` (`main.cpp:913`) and `syncTask` (`main.cpp:964`) call
`peek()`, build the payload, and establish the in-flight condition. Under this
design they must not. They reduce to cadence: set a "delivery due" signal at
`TELEMETRY_PUBLISH_MS` in `NORMAL` and `SYNC_BATCH_DELAY_MS` in `SYNCING`.
`connectionTask` acquires the pinned head, builds, publishes, and processes the
ACK.

Consequence worth noting: with acquire → build → publish inside one
`connectionTask` iteration, telemetry no longer transits `g_publishQueue`, so
`QUEUED` never spans a scheduling boundary and lease-generation validation stops
being load-bearing for telemetry. `QUEUED` and generation are specified for a
future deferred path in §4.2 but are not implemented in the initial landing
(see D3). `g_publishQueue` remains for non-leased messages such as E-Stop.

`syncTask`'s drain-complete check moves to `connectionTask`, which can evaluate
`isEmpty()` immediately after each commit rather than on a 100 ms poll.

## 4. Lease state machine

Initial-landing lease fields: `identity {boot_id, sequence_id}`,
`ever_published`, `publish_calls`, `successful_publishes`,
`connected_wait_ms`, `sent_at_ms`, and `next_attempt_at_ms`. `generation`
belongs only to the deferred publishing contract in §4.2 and is not present in
the initial implementation.

`publish_calls` counts every `publish()` invocation, successful or not;
`successful_publishes` counts only those returning true. Both are needed: a
budget keyed on successes alone cannot terminate a lease that never publishes
(§6).

`ever_published` is independent of phase and is the sole ACK-eligibility
predicate. Gating on phase is wrong: `RETRY_PENDING` is reachable from a publish
failure, where the record was never transmitted and a matching ACK could only be
stale or erroneous. (In the current code it is also reachable from an enqueue
failure at `main.cpp:202`; §3.1 removes telemetry from `g_publishQueue`, so that
path disappears.)

### 4.1 Initial inline-publishing state machine

With `connectionTask` acquiring, building, and publishing in one iteration
(§3.1), only three phases are observable: `IDLE`, `AWAITING_ACK`, and
`RETRY_PENDING`. Acquisition, payload construction, and the synchronous
`publish()` call are one transition action **with respect to MQTT callbacks
only**: no ACK can be observed partway through them, because `connectionTask`
is the sole MQTT owner.

That is not general atomicity, and the distinction matters. `filterTask` and
`sensorTask` run on core 1 and can call `push()` — including a protected
eviction that relocates the pinned record — at any point inside that window.
What protects the record there is the **pin**, not the iteration boundary.
Reading "one transition action" as "nothing else can interleave" is the same
assumption that produced §1.1, so it is stated explicitly here. Test 6 covers
the window.

| # | From | To | Trigger | Actor | Buffer effect |
|---|---|---|---|---|---|
| 1 | `IDLE` | `AWAITING_ACK` | delivery due, buffer non-empty, connected; acquire + build + `publish()` returns true | connectionTask | pin acquired; identity assigned; per-lease counters zeroed; `publish_calls++`, `successful_publishes++`, `ever_published = true`, timers set |
| 2 | `IDLE` | `RETRY_PENDING` | same action, but `publish()` returns false | connectionTask | pin acquired and held; `publish_calls++`; `ever_published = false`; retry backoff set |
| 3 | `AWAITING_ACK` | `IDLE` | ACK matches pinned identity | connectionTask | `commitPinnedHead()` validates + pops under one lock |
| 4 | `AWAITING_ACK` | `RETRY_PENDING` | ACK timeout (`MQTT_ACK_TIMEOUT_MS`) | connectionTask | pin held; retry time set |
| 5 | `AWAITING_ACK` | `RETRY_PENDING` | MQTT disconnect | connectionTask | pin held; connected-time accrual stops |
| 6 | `RETRY_PENDING` | `AWAITING_ACK` | retry due, connected, `publish()` returns true | connectionTask | same pin; `publish_calls++`, `successful_publishes++`, `ever_published = true`, ACK timer set |
| 7 | `RETRY_PENDING` | `RETRY_PENDING` | retry due, connected, `publish()` returns false | connectionTask | same pin; `publish_calls++`; `ever_published` unchanged; next backoff set |
| 8 | `RETRY_PENDING` | `IDLE` | ACK matches pinned identity and `ever_published` | connectionTask | `commitPinnedHead()`; avoids a duplicate write |
| 9 | `RETRY_PENDING` | `IDLE` | connected-time/publish-call budget exhausted | connectionTask | `abandonPinnedHead()`; record an abandonment outcome, not an asserted delivery loss |

`connected_wait_ms` accrues from acquisition through commit or abandonment, but
only during intervals in which MQTT is connected. It accrues in both active
lease phases, including while a retry backoff is pending.

Every commit or abandonment arrow is conditional on the corresponding
`BufferManager` operation returning true. An identity-validation failure inside
`commitPinnedHead()` or `abandonPinnedHead()` increments
`lease_internal_errors` and leaves the lease phase, pin, and retry state
unchanged. Clearing controller state after a failed buffer mutation would
recreate the split-state failure this design is meant to remove.

When multiple events are ready in one `connectionTask` iteration, process
connection-state accounting first, then ACKs, then timeout/abandonment, then a
due publish attempt. A matching ACK therefore wins over a timeout or abandonment
budget that matured in the same iteration. Disconnect may first move
`AWAITING_ACK` to `RETRY_PENDING`, but the same-iteration ACK remains eligible
through `ever_published` and can still commit the record.

### 4.2 Deferred-publishing contract (future only)

`generation` exists to cancel an outbound message whose lease has since been
committed or abandoned. It is only meaningful when a leased message can outlive
the iteration that built it, which the inline design prevents. Specified here in
full so the mechanism is implementable rather than half-built:

1. Every leased outbound message copies `lease.generation` at enqueue time,
   alongside `boot_id` and `sequence_id`.
2. Before publishing a leased message, `connectionTask` compares the message's
   generation **and** identity against the active lease.
3. On mismatch, the message is discarded **without calling `publish()`**.
4. `generation` increments on acquire, on commit, and on abandonment.
5. Deferred publishing adds `READY_TO_SEND` and `QUEUED`. A successful publish
   moves `QUEUED → AWAITING_ACK`; failure moves `QUEUED → RETRY_PENDING`.
6. A matching ACK commits from every phase where `ever_published` can be true,
   including a queued retry. Committing that retry increments generation, so
   rules 2-3 discard its now-stale outbound message.

Rules 2-3 make a queued retry cancellable and therefore make accepting its late
ACK safe. None of this subsection is implemented in the initial landing — see
D3.

Non-transitions that must be explicit in code:

| Event | Effect |
|---|---|
| ACK arrives with no active lease | `ack_stale++`. No state change. |
| Active lease exists but ACK identity does not match it | `ack_mismatch++`, regardless of `ever_published`. Changes **no** buffer, lease, queue, or retry state. This is the current regression: `main.cpp:521-525` clears the flag. |
| ACK identity matches the active lease but `ever_published == false` | `ack_stale++`. No state change. |
| `push()` overflows against a pinned head | Relocate pinned record, evict second-oldest, `protected_evictions++`. Pin **not** released. |

## 5. BufferManager API

```cpp
enum class PushResult { OK, EVICTED_OLDEST, EVICTED_PROTECTED, REJECTED_NEWEST, NOT_INITIALISED };

struct RecordIdentity {
    uint32_t boot_id;
    uint32_t sequence_id;
};

struct PushOutcome {
    PushResult result;
    bool record_lost;
    RecordIdentity lost;
};

PushOutcome push(const TelemetryRecord& rec);
bool acquirePin(TelemetryRecord& out);                         // pin + record copy, one lock
bool commitPinnedHead(uint32_t boot_id, uint32_t seq);         // validate + pop, one lock
bool abandonPinnedHead(uint32_t boot_id, uint32_t seq,
                       RecordIdentity& abandoned);             // validate + drop + count
```

Extend the existing atomic `BufferStats` snapshot with cumulative
`evicted_oldest`, `protected_evictions`, `rejected_newest`, and `abandoned`
counters. Here `abandoned` counts local lease-release decisions, not confirmed
delivery loss. `connectionTask` uses that snapshot for periodic diagnostics;
`buffer_unavailable` and `diagnostic_events_lost` live in `LossJournal` because
they can occur when the buffer is unavailable or the journal itself is full.
The buffer's cumulative `abandoned` value maps to diagnostic
`lease_abandoned`; connectionTask additionally increments exactly one subtype,
`lease_abandoned_unpublished` or `lease_abandoned_after_publish`.

`abandonPinnedHead()` replaces an earlier `releasePin(bool dropRecord)`. A
boolean parameter makes it too easy to unpin a transmitted record without
committing or counting its loss; a named operation encodes the intent and lets
the implementation guarantee that abandonment always counts. It validates the
requested identity under the buffer mutex and returns the identity it actually
removed. It does **not** emit MQTT or mutate the diagnostic journal:
`BufferManager` has neither the lease timers nor ownership of the network path.
`connectionTask` records the returned identity and its lease metadata as a
delivery-outcome event in `LossJournal`, then publishes the event later. A
second operation
`cancelUnpublishedPin()` would be needed only for releasing a lease that was
never published — no transition in §4 reaches that, so it is not added until a
caller exists.

`push()` must return the exact identity lost for all four lossy outcomes. For
`EVICTED_OLDEST` and `EVICTED_PROTECTED`, it copies the victim identity before
overwriting or moving any slot while holding the mutex. For `REJECTED_NEWEST`
and `NOT_INITIALISED`, the lost identity is the incoming record. Only `OK` has
`record_lost == false`. The producer forwards lossy outcomes to the thread-safe
`LossJournal`; it never derives the victim from a later `peek()`.

`push()` returning `false` currently means only "not initialised", which is why
`main.cpp:668` logs `"buffer full, fault record lost"` on a condition that
cannot mean that. The enum removes the ambiguity; fix that log with it.

### 5.1 LossJournal boundary

`LossJournal` accepts `{policy, lost identity}` observations for confirmed local
losses from every buffer producer, plus delivery-outcome observations for lease
abandonment from `connectionTask`. An abandonment after a successful publish is
not labeled as loss because its downstream result is unknown until reconciled.
The journal serializes updates under its own mutex, coalesces only adjacent
identities, and keeps a bounded RAM queue of closed ranges/events for
`connectionTask` to emit.
`connectionTask` periodically asks it to close an expired open range before
draining that queue; a timer does not depend on another loss arriving. The
journal never calls MQTT itself. If its bounded queue overflows, it increments
a separate `diagnostic_events_lost` counter so exact attribution can degrade to
the device-reported/unattributed classification rather than disappear silently.

### 5.2 Second-oldest eviction

At capacity with a pinned oldest record at read index `R`, preserve the pin and
shed the second-oldest, O(1):

```
_buffer[(R+1) % cap] = _buffer[R];   // pinned record moves to the next slot
_readIndex = (R+1) % cap; _count--; protected_evictions++;
_buffer[_writeIndex] = rec; _writeIndex = (_writeIndex+1) % cap; _count++;
```

Result: the pinned record remains the oldest record at `_readIndex`, the new
record is newest, and FIFO order holds.
**The pin must be identity-based, not a slot index** — this operation moves the
pinned record, so a slot pointer would be invalidated by the very step that
protects it.

Correct for **exactly one** pinned oldest record, from capacity 2 upward. At
capacity 1 it degenerates to overwriting the pinned record — the exact bug being
fixed.
Guard it as:

```cpp
if (_hasPinnedHead && _count == 1) -> REJECTED_NEWEST
```

**Multiple simultaneous pins are explicitly out of scope.** An earlier draft
guarded on `_count - _pinned_count == 0` and cited `SYNC_BATCH_SIZE`'s reserved
multi-in-flight design. That is false generality: with two pinned records at `T`
and `T+1`, copying `_buffer[T]` into `_buffer[T+1]` overwrites a pinned record.
The guard would look safe while the algorithm silently destroyed protected data.
Supporting multiple in-flight records requires a different eviction algorithm
and API, not a generalised capacity condition — a guard that advertises
generality the algorithm lacks is worse than one that does not.

## 6. Abandonment policy

Budget accrues **only while MQTT is connected**. Disconnected wall-clock must
not consume an ACK retry budget, since ACK receipt is impossible then.

Abandon when:

```
publish_calls >= ABANDON_MAX_PUBLISH_CALLS
  && connected_wait_ms >= ABANDON_MIN_CONNECTED_MS
```

`protected_evictions` remains an operational pressure counter but is not an
abandonment trigger. With the proposed defaults, connected-time abandonment
matures around 15 seconds while 1000 protected evictions require about 500
seconds at 2 Hz, so the pressure term cannot win while connected. While
disconnected, no drain is possible and the pin costs only one buffer slot;
discarding it under pressure would give up the retry guarantee without
unblocking delivery. Connected and ACK-capable time directly measures the
head-of-line blocking the policy needs to bound.

Failed publishes must be **paced**. `publish() == false` moves straight to
`RETRY_PENDING`, and without a retry-time guard the next delivery signal would
retry it 100 ms later in `SYNCING`. With the cap reached at call 5 (500 ms) but
the time condition not maturing until 15 s, the firmware would make **150
failed `publish()` calls** in that window. The constants below were sized for
the success path, where
pacing comes from the 3 s ACK timeout; the failure path has no such pacing.

Add `next_attempt_at_ms` to the lease. A failed publish schedules the next
attempt at an exponential backoff starting at `ABANDON_RETRY_BACKOFF_MS`
(1000 ms) and doubling. The retry transitions in rows 6-7 fire only when
`millis() >= next_attempt_at_ms`.
Once `publish_calls >= ABANDON_MAX_PUBLISH_CALLS`, **no further `publish()`
calls are made** while the connected-time condition matures.

With a 1000 ms doubling backoff, calls land at 0, 1, 3, 7, and 15 s — so call 5
coincides with `ABANDON_MIN_CONNECTED_MS`, both conditions mature together, and
the rationale in the table below becomes true for the failure path as well as
the success path. Backoff persists across reconnects within a lease: a
deterministic cause such as an oversized payload is not repaired by reconnecting.

The budget keys on `publish_calls`, **not** on successful publishes. A budget
counting only successes cannot terminate a lease whose `publish()` fails
deterministically — payload over the transport ceiling (§1.4), an oversized
topic, or a persistent client-state fault. Without the publish-call budget,
successes would stay at zero forever, pinning the buffer permanently and
stalling delivery with no diagnostic.
`successful_publishes` is retained to attribute the abandonment reason.

Proposed starting values, to be tuned on hardware:

| Constant | Value | Rationale |
|---|---|---|
| `ABANDON_MAX_PUBLISH_CALLS` | 5 | Success path: 5 × `MQTT_ACK_TIMEOUT_MS` (3000) = 15 s. Failure path: 5 backoff steps = 15 s |
| `ABANDON_RETRY_BACKOFF_MS` | 1000 | Doubling; paces failed publishes so both conditions mature together |
| `ABANDON_MIN_CONNECTED_MS` | 15000 | Both conditions required, so a fast retry storm cannot abandon early |

Reason codes: `ack_budget_exhausted` (`successful_publishes > 0`),
and `publish_failure_budget_exhausted` (`successful_publishes == 0`). The former
means delivery is unknown, not failed: one or more MQTT publishes were accepted,
but no matching application ACK arrived. The latter is a confirmed local loss
under the client contract because no publish attempt was accepted.

Because the pin is held across disconnect, a record published-but-unACKed just
before an outage becomes the head of the post-reconnect drain. The budget
therefore bounds recovery time from every outage, not only pathological ones.

## 7. Diagnostics

New topic `sensor/<node>/diag`, separate from telemetry. Three message kinds,
all carrying `boot_id` and a monotonic `diag_id` in **its own ID space** — a
diagnostic record is control-plane evidence about the delivery pipeline, not
telemetry, and must not consume a `sequence_id` or perturb the sequence it
describes.

Lease abandonment is not itself proof of delivery loss. It means the firmware
stopped retaining and retrying a record after its bounded budget expired. If
`successful_publishes > 0`, the record may already be in InfluxDB and the
missing ACK may be the only failure. The confirmed local loss policies
`evicted_oldest`, `evicted_protected`, `rejected_newest`, and
`buffer_unavailable` each create sequence gaps. If exact classification is a
requirement, every loss policy must journal identities, not just lease
abandonment. Per-record MQTT events are
infeasible at 2 Hz saturation, but adjacent loss identities can be compressed
into an exact range:

```json
{
  "boot": 4,
  "diag_id": 19,
  "kind": "loss",
  "policy": "evicted_protected",
  "first_seq": 1200,
  "last_seq": 1847,
  "count": 648
}
```

A range must close on sequence discontinuity, policy change, span, or timer.
Two separate loss periods under the same policy need not be adjacent:

```
evict 100-110   |  deliver 111-150  |  evict 151-160
```

Closing only on policy change would emit `100-160`, falsely reporting 111-150 as
lost — and since an exactly-explained range is the strongest verdict the checker
issues, that would attribute *delivered* records as attributed loss. Close or
split whenever:

```
boot != current.boot || sequence != current.last_seq + 1
```

This is reachable in production, not just in tests: during `SYNCING`, drain and
production compete, so the buffer can saturate, drop below capacity, and
saturate again. Also, sequence IDs are assigned before `push()` by more than one
producer, so task scheduling can make ring order differ from sequence order.
Contiguity is an opportunity checked per observation, never an invariant of an
overflow policy. `rejected_newest` describes discarding the incoming record; it
does not remove the oldest record at `_readIndex`.

Sequence wrap is out of reach within a boot: `sequence_id` is `uint32` and at
2 Hz would take ~68 years to wrap, and `boot_id` increments make it moot. The
`last_seq + 1` comparison uses `uint32` arithmetic, so a true wrap would read as
contiguous — accepted at that timescale, noted here so it is a decision rather
than an oversight.

Ranges are otherwise emitted on close — policy change, a bounded max span, or a
publish interval — not per evicted record.

Lease-abandonment outcome event:

```json
{
  "boot": 4,
  "diag_id": 17,
  "kind": "lease_abandonment",
  "abandoned_boot": 4,
  "abandoned_seq": 4821,
  "reason": "ack_budget_exhausted",
  "delivery_outcome": "unknown_after_publish",
  "ever_published": true,
  "publish_calls": 5,
  "successful_publishes": 5,
  "connected_wait_ms": 15000
}
```

For `publish_failure_budget_exhausted`, emit `ever_published: false` and
`delivery_outcome: "not_published"`. For `ack_budget_exhausted`, always emit
`delivery_outcome: "unknown_after_publish"`; never label it `lost` merely
because the firmware stopped retrying.

Periodic cumulative counters (not on `TelemetryRecord`: adding four `uint32`
fields to the 48-byte record would grow the ring by ~800 KB and change the MQTT
payload, bridge parser, `telemetry-schema.md`, and Grafana panels, for data that
changes rarely):

```json
{
  "boot": 4,
  "diag_id": 18,
  "kind": "counters",
  "evicted_oldest": 0,
  "protected_evictions": 42,
  "rejected_newest": 0,
  "buffer_unavailable": 0,
  "lease_abandoned": 1,
  "lease_abandoned_unpublished": 0,
  "lease_abandoned_after_publish": 1,
  "diagnostic_events_lost": 0,
  "lease_internal_errors": 0,
  "ack_mismatch": 0,
  "ack_stale": 3
}
```

Counters give magnitude and self-heal — any later message re-reports the
cumulative total, so a lost diagnostic does not lose the count. Events give
identity. Both are needed: a bare counter cannot say *which* gap is explained,
and a best-effort event can itself be lost during the outage that caused it.
`lease_abandoned_after_publish` is an outcome counter, not a confirmed-loss
counter, and must never be subtracted from an unrelated gap by magnitude. The
exact record identity comes from `PushOutcome` or `abandonPinnedHead()`, is
recorded by `LossJournal`, and is never reconstructed from buffer state after
mutation.

The diagnostic name `buffer_unavailable` maps exactly to
`PushResult::NOT_INITIALISED`; it is the loss policy used when the incoming
record cannot enter an unavailable buffer.

**Cumulative counters reset to zero at boot.** A decrease across records is a
boot marker, not corruption, and the checker must encode that. Counters
self-heal only within a boot; across a reboot they carry no history, which is
the substance of D2.

## 8. Integrity-check classification

`integrity_check.py` gains a **four-way** result per gap:

| Result | Meaning | Verdict |
|---|---|---|
| **Contiguous** | Sequence complete after dedupe | PASS |
| **Exactly explained** | Gap identity or range matches a loss event | Loss, attributed |
| **Device-reported, unattributed** | Counters reconcile by magnitude only; no event covers these identities | Loss, unattributed |
| **Unexplained** | No counter or event accounts for the gap | FAIL |

The third category exists because **magnitude reconciliation is not proof of
identity.** An earlier draft folded it into "explained": a gap of one alongside
an overflow counter that also advanced by one would be marked explained, even
when the counter increment and the missing record are causally unrelated. That
is precisely the laundering the rule below is meant to prevent, so magnitude
agreement gets its own weaker verdict rather than borrowing the strong one.

Exactly-explained and device-reported gaps are **both still real data loss**.
They are expected policy behaviour rather than corruption, and must be reported
as loss — never converted into an unconditional pass. A counter-driven
classifier is exactly the thing that decays into a way to launder failures;
this rule is the guard.

### 8.1 Lease-abandonment reconciliation

Lease-abandonment events require a separate identity reconciliation because an
event may refer to a record that was delivered successfully. They are not fed
blindly into loss-counter subtraction.

| Result | Condition | Meaning |
|---|---|---|
| **Abandoned but delivered** | Referenced identity exists in InfluxDB and `ever_published == true` | ACK path failed or was too slow; delivery succeeded; no sequence loss |
| **Attributed abandonment gap** | Referenced identity is absent and falls inside an observed sequence gap | Real observed data loss associated with the bounded-abandonment decision |
| **Unexpected delivery after local publish failure** | Referenced identity exists but `ever_published == false` | Transport-contract anomaly, partial-write edge case, or identity collision; investigate |
| **Indeterminate abandonment** | Referenced identity lies outside the telemetry query's covered identity/time range | No delivery conclusion; do not use the event for reconciliation |

The checker must query the referenced `boot_id + sequence_id` directly, or prove
that its telemetry query covers that identity, before declaring it absent. A
diagnostic event inside a recent time window may reference an older telemetry
record outside that window. Treating absence from the window as delivery loss
would create a false gap.

`lease_abandoned_after_publish` never explains another gap by magnitude. An
exact identity match can attribute an observed gap; an identity found in
InfluxDB instead produces `Abandoned but delivered`. The unpublished-abandonment
counter may support the weaker device-reported/unattributed category, but only
within the same boot and covered query interval.

**A lost after-publish abandonment event therefore degrades to `Unexplained`
(FAIL), not to the unattributed category — and that is intentional.** The event
is the only exact path, since magnitude reconciliation is barred for this
counter by the rule above. If the event is lost (journal overflow, or RAM-only
retention across a reboot per D2) and the record was genuinely not persisted,
the resulting gap is a record the device published and the pipeline did not
store. That warrants investigation rather than a softer verdict, so the
classifier is correct to fail it. Recorded here so the outcome reads as a
decision rather than as an overlooked counter.

## 9. Open decisions

**D1 — Task architecture scope.** §3.1 requires `telemetryTask` / `syncTask` to
stop touching the buffer. Once they are pure cadence, they could collapse into
an interval check inside `connectionTask` (~4 lines replacing two tasks).
*Recommendation:* reduce them to signalers now, track the collapse separately.
Bundling a structural refactor with a correctness fix makes the regression test
harder to attribute, and the 6-task table is published in `README.md`,
`project-context.md`, `architecture.md`, and the status notes.

**D2 — Diagnostic durability.** RAM-only diagnostics lose abandonment identities
across a reboot. A boot boundary explains why *numbering resets*; it does not
explain a gap created earlier within the previous boot. If an abandonment
occurs, later records in that boot are delivered, the diagnostic is lost, and
the device then reboots, the checker sees an unexplained gap from a prior boot.
The cost is sharper than lost attribution alone: per §8.1, a lost after-publish
abandonment event cannot fall back to magnitude reconciliation, so RAM-only
retention converts a known policy outcome into an `Unexplained` FAIL whenever
that event is lost and the record was not persisted. That is the correct
verdict, but it means the durability choice changes test results, not just
diagnostic richness.

*Recommendation:* RAM-only for this landing, with the limitation stated in
`store-and-forward-status.md`. Revisit if a hardware run produces an unexplained
gap. NVS persistence would need batched writes for flash wear, following the
existing fault-counter discipline of writing on transition only.

**D3 — Retain `QUEUED` and generation?** `QUEUED` is unreachable and generation
is unnecessary once `connectionTask` builds and publishes inline (§3.1).
*Recommendation, revised:*
**specify fully, implement neither.** §4.2 defines the deferred generation
contract so it is implementable when needed, while §4.1 is the complete initial
state machine. An earlier revision recommended retaining both "as insurance",
which was wrong: a mechanism with no reachable caller is never exercised, so it
is untested at exactly the moment someone first relies on it. Dead paths that
look live are worse than an absent feature and a written contract.

**D4 — Abandonment thresholds.** §6 values are estimates. Tune during hardware
validation.

## 10. Test plan

**Prerequisite: there is no host test harness, and current code cannot be
tested in place.** `firmware/` has no `test/` directory and `platformio.ini`
defines only `env:esp32s3-n16r8`; CI runs `pio run` only.

Two distinct coupling problems, neither solved by mutex stubs alone:

- The ACK state is file-static in `main.cpp` (`g_bufferRecordInFlight`,
  `g_inFlightBoot/Seq`, `g_ackBoot/Seq`) and lives inside `connectionTask`,
  bound to Arduino, FreeRTOS event groups, PubSubClient, and hardware setup.
  It cannot be linked natively as written.
- `BufferManager` depends on `Arduino.h`, `freertos/FreeRTOS.h`,
  `freertos/semphr.h`, and `esp_heap_caps.h`. It needs an allocator **and**
  mutex abstraction, or extraction of a pure storage core.

So test 1 cannot target `main.cpp` directly. Revised approach:

1. **Mechanically** extract the legacy ACK state transition behind a test seam,
   changing no behaviour — including `connectionTask`'s ACK-before-drain
   ordering, which is what opens the window.
2. Demonstrate the R0/R1 failure against that extracted legacy behaviour.
3. Replace it with the lease controller; the same test now passes.
4. Test the ring algorithm separately against an allocator/mutex abstraction.

Step 1 is load-bearing and must be reviewed as behaviour-preserving. An
extraction that accidentally repairs the ordering yields a passing test that
proves nothing — the seam is only as trustworthy as its fidelity to the
original.

| # | Test | Must fail before the fix |
|---|---|---|
| 1 | **R0/R1 regression** — duplicate ACK for R0 after R0 is committed, while R1 is acquired but before R1 is published | **Yes** |
| 2 | ACK never pops a record whose identity does not match the pinned head | Yes (peek/pop race, full buffer) |
| 3 | Overflow while `AWAITING_ACK` preserves the pinned record | Yes |
| 4 | Capacity-1 with a pinned head rejects the newest record | Yes |
